# Security model

This experimental companion imports public keys and requests signatures from Ledger after explicit phone review. It never requests, imports or stores wallet private keys or recovery phrases. Deterministic secret keys in the offline tests are public fixture vectors, never user wallet keys.

`SerializedTransport` enforces `ReadOnlyPolicy` at the APDU boundary. Permitted commands are Bitcoin `E1/00` (extended public key), Ethereum/TRON `E0/02` (public key/address), Cardano `D7/00` (version), `D7/10` (extended public key) and `D7/11` (address). APDU lengths and transport sequence numbers are checked. Ethereum/TRON public keys must match the returned device address; Cardano derived address is compared with the device result before display confirmation. Bitcoin requests on-device xpub display. This allowlist is tested, but it is not an independent security audit.

v0.2 adds a separate, chain-bound `LedgerPermit`, minted only by phone confirmation for one prepared transaction, or by a public-address verification action. Signing permits allow Bitcoin `E1/04` plus fingerprint/xpub/address and `F8/01` continuation; Ethereum `E0/04` and authenticated ERC20 display metadata `E0/0A`; TRON `E0/04`; Cardano `D7/21` with the official v7/v8 adapters. They have a bounded command budget and are revoked when the operation ends. TRON blind-hash signing `E0/05`, arbitrary messages, ECDH and unrelated commands remain blocked. TRON address truncation must be disabled before signing.

Amounts use integer smallest units and exact decimal values. BTC verifies previous transaction IDs, values and scripts against derived ownership. Cardano checks derived payment ownership and preserves other selected native assets in change. ETH pins mainnet chain ID 1; only reviewed native/USDT transfer payloads are built. The device signature is checked against the exact unsigned transaction and imported public keys. Cardano also compares the device transaction hash and verifies every witness. BTC/Cardano final signed size and fee are checked before broadcast.

The bundled JavaScript/WebAssembly engine has no network, file URLs, content access or navigation. User text is JSON encoded, never executed as JavaScript. The bridge exposes only the active operation's authorized Ledger transport. Ethereum metadata resolution is explicit and offline, with no automatic blind-signing fallback. Drafts expire after five minutes and must be prepared/reviewed again after expiry or edits.

The transaction ID and submission state are persisted before a single-attempt broadcast. Timeout or an unexpected node response is treated as uncertain and checked by ID; neither re-signing nor resubmission happens automatically. Successful chain receipts must match the saved ID where returned. Pending account removal/sending is blocked. Status polling is separate from full balances; a post-confirmation balance attempt is persisted before querying so restarts do not repeat it. A dropped or indefinitely unknown transaction needs investigation through its explorer/provider; the app does not implement replacements or cancellation.

Portfolio data and provider keys use AES-GCM with an Android Keystore key and an atomic file. Encryption failure blocks overwrite rather than silently resetting the portfolio. HTTPS-only requests and disabled cleartext traffic limit accidental credential exposure. API error messages omit key-bearing request paths. Untrusted token symbols never establish Binance pricing identity.

New BTC/Cardano receiving addresses are derived locally from imported public account keys. Their indices are persisted before display, with bounded generation and discovery. Address verification requests the selected nonzero receive path while retaining the original account/stake identity; a device result differing from the selected address fails. BTC transaction-history query failures stop generation. Cardano generation is offline; another wallet may already have used the same derived index. No software-wallet secret is created. Losing app data loses issued-index bookkeeping, so independent wallet recovery may need a larger discovery gap.

Physical Flex USB/BLE interoperability and device approval/rejection/disconnection flows still require hardware testing. Bluetooth pairing and Ledger firmware provide their own trust boundary; phone-side code cannot prove firmware authenticity. Review device-displayed addresses, amounts, network and token before approving an import or transaction. Never enter a recovery phrase into this app.

Report a vulnerability privately to the repository owner through their GitHub profile contact details. Do not publish credentials or personal account xpubs in an issue. There is no claim of a formal audit or production certification.
